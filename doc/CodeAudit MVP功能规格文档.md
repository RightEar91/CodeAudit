# CodeAudit — MVP 功能规格文档

> 版本：v1.0
> 日期：2026-05-21
> 基于设计文档版本：1.0

---

## 1. 产品概述

CodeAudit 是一个**完全本地运行**的 AI 代码审查平台。源码不出内网，通过本地 Ollama 部署的 Qwen3:8b 模型进行代码审查，结果通过 Web 管理台展示。

### 1.1 核心价值主张

- **安全可控**：代码绝不离开本地网络，杜绝源码泄露
- **轻量易用**：N100 小主机即可运行，Docker Compose 一键部署
- **开箱即用**：Git 仓库直接接入，diff 级别的 AI 审查

## 3. 功能拆解 — 用户故事与验收标准

### 3.1 Git 仓库接入（P0）

**用户故事**

> 作为一名开发者，我希望能将本地 Git 仓库接入 CodeAudit，这样系统能读取我的代码变更进行审查。

**子功能**

#### US-1.1：添加项目（手动指定仓库路径）

- **验收标准**
  - 用户可在 Web 界面填写项目名称和本地 Git 仓库绝对路径
  - 系统校验路径是否存在且为有效的 Git 仓库（含有 `.git` 目录）
  - 校验通过后，项目写入 `ca_projects` 表
  - 校验失败时返回明确错误提示
  - 支持 Java 语言标记（默认）

#### US-1.2：项目列表查看

- **验收标准**
  - 展示所有已接入项目，字段：项目名称、仓库路径、当前分支、创建时间
  - 支持按名称搜索
  - 支持删除项目（级联删除关联的审查记录和问题）

#### US-1.3：提取 commit diff

- **验收标准**
  - 用户输入起始 commit 和/或目标 commit（默认自动取 HEAD~1..HEAD）
  - 系统调用 JGit 提取 Java 文件变更的 diff
  - 返回结构化数据：文件路径、变更类型（ADD/MODIFY/DELETE）、diff 内容、增删行数
  - 仅过滤 `.java` 文件变更

#### US-1.4：提取分支间 diff

- **验收标准**
  - 用户输入源分支名和目标分支名
  - 系统执行 `git diff fromRef..toRef -- *.java`
  - 返回与单 commit 相同的结构化 diff 数据

### 3.2 代码 Diff 审查（P0）

**用户故事**

> 作为一名开发者，我希望选中一次代码变更后能自动触发 AI 审查，快速发现安全漏洞、性能问题和代码规范问题。

#### US-2.1：手动触发审查

- **验收标准**
  - 用户在项目详情页点击"新建审查"，选择 diff 范围
  - 系统异步提交审查任务，状态变更为 `processing`
  - 前端轮询或 WebSocket 展示进度
  - 审查完成后状态变更为 `completed`，触发结果展示

#### US-2.2：LLM 审查处理

- **验收标准**
  - 系统将 diff 逐文件/逐块送入 Ollama（Qwen3:8b）
  - Prompt 中注入启用的规则指令
  - LLM 返回结构化 JSON（issues 数组）
  - 每条 issue 包含：严重程度、分类、行号、描述、修复建议
  - 系统解析 JSON 并写入 `ca_issues` 表
  - 解析失败时任务状态置为 `failed`，记录错误信息

#### US-2.3：审查结果展示

- **验收标准**
  - 报告页顶部展示总览：总问题数、高危/中危/低危数量、耗时
  - 问题按严重程度降序排列（HIGH → MEDIUM → LOW）
  - 每条问题展示：严重级别图标、分类标签、文件路径+行号、问题描述、修复建议
  - 支持"查看代码"展开 diff 上下文
  - 支持"标记已修复"和"标记已忽略"操作

#### US-2.4：审查取消

- **验收标准**
  - 进行中的审查可被用户取消
  - 取消后状态置为 `failed`，备注"已取消"

### 3.3 Web 管理台（P0）

**用户故事**

> 作为一名开发者，我希望通过浏览器访问 CodeAudit，完成项目管理、触发审查、查看结果等所有操作。

#### US-3.1：页面路由

- **验收标准**
  - `/` 或 `/projects`：项目列表首页
  - `/projects/:id/reviews`：指定项目的审查历史列表
  - `/reviews/:id`：审查报告详情页
  - `/rules`：规则管理页（P1 阶段）
  - `/settings`：系统设置页

#### US-3.2：项目列表页

- **验收标准**
  - 展示所有项目卡片或表格
  - 每条记录支持"查看审查记录"和"删除"操作
  - 顶部有"新建项目"按钮

#### US-3.3：审查记录页

- **验收标准**
  - 展示指定项目的所有审查记录
  - 表格列：审查标题、状态、问题数量、创建时间、耗时
  - 状态用颜色区分（完成=绿，处理中=蓝，失败=红）
  - 支持按状态筛选
  - 每条记录可点击进入详情页

#### US-3.4：审查报告详情页

- **验收标准**
  - 按 US-2.3 标准展示
  - 顶部有"导出 PDF / JSON"按钮

#### US-3.5：系统设置页

- **验收标准**
  - Ollama 地址配置（默认 `http://localhost:11434`）
  - 模型名称配置（默认 `qwen3:8b`）
  - 设置持久化到数据库或配置文件

### 3.4 规则引擎（P1）

**用户故事**

> 作为一名开发者，我希望能看到代码被哪些规则审查，并能自定义审查指令，让 AI 按我的团队规范来检查代码。

#### US-4.1：查看内置规则列表

- **验收标准**
  - 规则列表页展示所有规则
  - 每条规则显示：名称、分类、目标语言、描述、启用状态
  - 内置规则标记不可删除

#### US-4.2：创建自定义规则

- **验收标准**
  - 用户可输入规则名称、选择分类、选择语言、编写 Prompt 指令
  - 创建后规则默认为启用状态
  - 自定义规则可编辑和删除

#### US-4.3：启停规则

- **验收标准**
  - 每条规则有启用/禁用开关
  - 仅启用状态的规则在审查时注入 Prompt

#### US-4.4：内置预置规则（MVP 交付时自带）

| 规则名 | 分类 | 描述 |
|--------|------|------|
| SQL 注入检查 | SECURITY | 检测 SQL 拼接、未参数化查询 |
| 空指针检查 | BUG | 检测 null 检查缺失、Optional 误用 |
| 性能优化 | PERFORMANCE | 检测 N+1 查询、String 拼接、重复对象创建 |
| 资源泄漏 | BUG | 检测流/连接/锁未正确关闭 |

### 3.5 审查报告导出（P1）

**用户故事**

> 作为一名开发者，我希望将审查报告导出为 PDF 或 JSON，方便存档或分享给团队成员。

#### US-5.1：导出 PDF

- **验收标准**
  - 报告详情页点击"导出 PDF"触发下载
  - PDF 包含：项目名、审查标题、审查时间、问题汇总（高/中/低计数）
  - 每条问题的描述和建议完整保留
  - 分页合理，中文正常渲染

#### US-5.2：导出 JSON

- **验收标准**
  - 报告详情页点击"导出 JSON"触发下载
  - JSON 结构与 `ca_issues` 表一致，包含所有字段
  - 可作为 CI/CD 脚本或其他工具的输入

---

### 3.6 多文件批量审查（P1）

**用户故事**

> 作为一名开发者，我提交了一个 PR 涉及十几个文件的变更，希望能一键审查所有变更，而不是逐个文件操作。

#### US-6.1：按分支全量审查

- **验收标准**
  - 用户选择源分支和目标分支，系统自动收集所有 `.java` 变更文件
  - 所有变更文件作为一次审查任务提交
  - 审查结果按文件分组展示（在报告详情页中按文件折叠/展开）
  - 报告汇总所有文件的问题统计

#### US-6.2：审查进度可感知

- **验收标准**
  - 多文件审查时，前端展示进度条（如：3/12 files reviewed）
  - 支持在审查进行中查看已完成文件的部分结果

## 5. 优先级合理性分析

### ✅ 合理部分

1. **Git 仓库接入 + Diff 审查 + Web 管理台 列为 P0** — 这是核心价值闭环的基础，缺任何一环都无法给用户交付可用产品。定位准确。

2. **规则引擎放 P1** — 虽然规则是差异化卖点，但没有规则引擎，使用硬编码 Prompt 在 MVP 阶段完全可以跑通。P1 是合理的。

3. **IDE 插件放 P3** — 需要跨平台 VSCode 扩展开发、发布、维护，对 4-6 周周期来说太重了。合理。

4. **多文件批量审查放 P1** — 这是真实场景下的刚需（一个 PR 很少只改一个文件），P1 是合适的。

### ⚠️ 建议调整项

#### 调整 1：异步任务队列 → 应明确纳入 P0/P1
- **问题**：设计文档提到了异步审查，但在功能列表中没有明确列出任务队列或异步执行机制。如果不做异步任务管理，批量审查和长时间运行会导致 HTTP 超时或浏览器白屏。
- **建议**：在 P0 中明确**异步审查状态管理**（pending → processing → completed → failed），在 P1 中增加**审查队列和进度反馈**。这属于基础设施，不是功能特性，但不做的话体验会断档。

#### 调整 2：审查结果标记（已修复/已忽略）→ 应纳入 P1
- **问题**：设计文档原型中提到了"标记已修复"按钮，但功能列表中没有对应条目。这是一个低成本高收益的交互。
- **建议**：P1 补充"问题状态管理"（open / resolved / ignored），配合 UI 操作。

#### 调整 3：考虑将"代码高亮展示"从后端纯文本移到 P1 前端增强
- **问题**：设计文档路线图把代码高亮放在第4周（第22-24天），但它直接影响报告页面的核心体验——没有代码高亮的审查报告只是一个问题列表。
- **建议**：提前到第2-3周，与报告详情页同步交付。可先不做完整 syntax highlight，至少做到 diff 代码行关联+行号显示。

#### 调整 4：report 中的 `fullContent` 字段建议评估必要性
- **问题**：`DiffBlock` 中包含了 `fullContent`（变更后完整文件内容），这会将大量完整文件文本送入 LLM Prompt。
- **建议**：MVP 阶段可以只传输 diff 块内容而非完整文件，大幅减少 tokens 消耗。若上下文不足再考虑增量补充。

### 🔍 遗漏的核心功能评估

| 潜在遗漏 | 是否需要加入MVP | 理由 |
|----------|----------------|------|
| **审查超时/重试机制** | ✅ 建议加入 P1 | LLM 调用可能超时或返回格式错误，需要超时控制和自动重试 |
| **Ollama 连接健康检查** | ✅ 建议加入 P1 | 系统启动和每次审查前应检测 Ollama 是否可达 |
| **基础指标/日志** | ✅ 建议加入 P1 | 用户需要知道每次审查的 token 消耗和耗时，用于模型调优决策 |
| **历史审查对比** | ❌ 可放后 | MVP 无需展示趋势 |
| **用户认证** | ❌ 可放后 | 单用户本地部署无需认证 |
| **WebSocket 实时通知** | ⚠️ 建议降级为轮询 | MVP 阶段轮询足以，WebSocket 增加复杂度 |

## 7. 验收总标准

### MVP 通过条件（全部满足即为 MVP 交付）

1. ✅ 用户可在 Web 界面添加 Git 项目（本地路径），系统校验仓库有效性
2. ✅ 用户可为项目选择 diff 范围，触发异步 AI 审查
3. ✅ 审查完成后，报告页展示问题列表（按严重度排序），含位置、描述、修复建议
4. ✅ 用户可按规则分类启停审查规则，自定义规则可创建、编辑、删除
5. ✅ 审查报告可导出为 PDF 和 JSON 文件
6. ✅ 支持 PR 级别多文件批量审查，结果显示按文件分组
7. ✅ 问题可标记为"已修复"或"已忽略"
8. ✅ Docker Compose 一键部署到 N100
9. ✅ 开源仓库发布（GitHub），含 README 快速启动指南

### 非功能性要求

- 单次审查（10 个文件以内）耗时不超过 5 分钟（视 N100 硬件性能）
- 审查过程中前端不超时、不白屏（异步 + 轮询进度）
- 系统启动时自动检测 Ollama 连接状态
